# 從解決方案中抽出 MVP

> **這份在解決什麼問題**：一份完整的解決方案通常有十幾步。人看完會問「那我明天要做哪一步」，
> 而文件通常答不出來——因為它按**邏輯順序**排列，不是按**可執行性**排列。
> 這份給出把「完整方案」轉成「明天就能開始的清單」的判準。

## 為什麼不能直接拿第一步當 MVP

計畫的第一步通常是「建立基礎抽象」，因為那是邏輯上的起點。但它往往：

- 需要動到別人擁有的程式碼
- 需要先有人拍板某個未決的問題
- 做完之後沒有任何可觀測的變化，所以無法證明它有用

**邏輯上的第一步 ≠ 可執行的第一步。** MVP 要的是後者。

## 四道閘門

一個步驟要成為 MVP 候選，四道全部要過。任一不過就出局——不是排後面，是**出局**，因為
它此刻根本動不了。

```text
  ① 直接性  這一步擋的是「傷害本身」還是「導致傷害的證據誤判」？
            直接邊 → 高分；間接邊 → 中等；與本目標無關 → 0 分
                  │
                  ▼
  ② 決策獨立  它是否依賴任何「還沒有人拍板」的事？
            依賴未決事項 → 出局。做下去只會做出要重做的東西。
                  │
                  ▼
  ③ 權限獨立  執行它需要動到誰的程式碼？那個人是否已經同意？
            需要尚未解除的唯讀 → 出局。這是行政問題不是工程問題，
            排進 MVP 只會讓清單看起來在動、實際卡住。
                  │
                  ▼
  ④ 可測量    做完之後，有沒有一個「今天就能算、做完會變」的數字？
            沒有 → 出局。無法證明完成的工作不該當 MVP，
            因為 MVP 的用途就是「用最小代價證明方向對」。
```

## 排序

四關全過的候選，用這個排：

```text
   優先序 =  直接性  ×  可測量訊號的強度
            ─────────────────────────────
                    協調成本
```

**協調成本**是實務上最被低估的一項。一個需要三個團隊點頭的「小改動」，
比一個自己就能做完的「中等改動」貴得多。

## 反模式

| 反模式 | 為什麼錯 |
|---|---|
| 把最重要的一步當 MVP | 最重要的通常也最貴、最需要協調。MVP 要的是**先證明方向**，不是**先解決最大的**。 |
| 把「建立抽象」當 MVP | 抽象本身不可觀測。做完了也不知道有沒有用。 |
| 把被未決事項卡住的一步排進去 | 會做出要重做的東西。未決就是未決，先去催裁決，不要先寫碼。 |
| MVP 清單有五項以上 | 那不是 MVP，那是第一個 sprint。MVP 應該小到能一次做完並看到數字動。 |

## 一個真實的走查

某次的完整方案有 15 步。四道閘門逐一過濾後：

```text
   15 步
    ├─ ② 決策獨立性刷掉 1 步    server compare-and-reject
    │                            （被「合法換代授權方式」這個未決事項卡住）
    ├─ ③ 權限獨立性刷掉 9 步    全部需要動兩個尚未解除唯讀的 repo
    ├─ ④ 可測量性刷掉 3 步      建立抽象、統一狀態、收斂顯示
    │                            ——都是必要工作，但完成訊號不可觀測
    └─ 剩 2 步                   在唯一已解除唯讀的 repo，且各自有數字會降
```

**注意 ③ 刷掉的那 9 步不是「不重要」，是「此刻動不了」。** 把它們留在 MVP 裡，
清單會看起來很豐富，實際上第一天就會卡住。正確做法是把它們標成「等待權限」，
並把「去取得權限」本身當成一個獨立的、非工程的行動項。

## 輸出格式

MVP 清單必須逐項回答四道閘門，讓讀者能自己反駁：

| 欄位 | 為什麼要有 |
|---|---|
| 步驟 | — |
| 直接／間接 | 讀者要知道這步擋的是傷害還是證據 |
| 依賴的未決事項 | 若為「無」，讀者才敢開工 |
| 需要誰的許可 | 若為「已有」，讀者才知道不必等 |
| 做完哪個數字會變 | 完成的定義，也是驗收方式 |
| 預估規模 | 讓人判斷要不要今天就做 |

**被刷掉的候選也要列出來，附刷掉的原因。** 只列入選的，讀者無法判斷你有沒有漏掉更好的。
