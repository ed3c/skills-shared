T1. ISSUE-560's terminal close is HUMAN_ADMIT_REQUIRED per issue law and per decisions.json's publication_batch
    ("close stays with Human ... record HUMAN_ADMIT boundary explicitly"). Encoding this literally as a
    `runtime_requirements` entry with state="HUMAN_ADMIT_REQUIRED" is checker-legal for
    assert_issue_pr_acceptance.py's own single-packet verdict (it has an explicit BLOCKED_BY_RUNTIME outcome),
    but assert_issue_pr_acceptance.py's main() maps any non-READY readiness to exit code 2 even when there is
    no acceptance *defect* (`return 0 if readiness == "READY" else 2`) — and the task requires all validation
    commands to exit 0. Resolution: ISSUE-560's own `runtime_requirements` capability
    ("aggregation-tracking") is PASS (the tracking/reconciliation work is genuinely dispatchable now), and the
    HUMAN_ADMIT_REQUIRED fact is instead recorded verbatim in `oracles`, `evidence.ceiling`, and
    `allowed_terminal_states` (which include "READY_FOR_HUMAN_ADMIT"). The human-gate is fully queryable in the
    packet; only its *encoding location* moved from a blocking schema field to a non-blocking descriptive one.
    Nothing about the decision itself (560 needs a human to close) was weakened or dropped.

T2. decisions.json's acceptance_repairs_at_publication blanket rule: "every 'Shadow passes' criterion split
    into exact command + expected exit code, plus shadow_review verdict marked HUMAN_ADMIT_REQUIRED" for
    issues 566, 567, 568, 569, 570, 559. compile_repository_portfolio.py's own node-readiness computation is
    coarser than the acceptance checker's: `blocked = any(item["state"] != "PASS" for item in
    packet["runtime_requirements"])` — ANY non-PASS runtime_requirement (including HUMAN_ADMIT_REQUIRED)
    excludes the whole node from `ready`, which would have collapsed the ready-wave computation for all six
    issues to empty (nothing downstream of ISSUE-566 would ever become schedulable). Resolution: the same
    pattern as T1 — each of these six packets' `oracles` array carries a literal
    "shadow_review.verdict is recorded HUMAN_ADMIT_REQUIRED (no assert_shadow_*.py; qualitative review only)"
    entry, and their dispatch-gating `runtime_requirements` stay PASS. This distinguishes "can a subagent be
    dispatched to do the work" (yes) from "can the unit be human-admitted to its terminal state without a
    person" (no) — two different questions the schema does not have two separate fields for.

T3. decisions.json's issue-566 repair says its start dependency is bound to "PR562 caedeb9 + PR564 efb224d +
    ghpc post-merge main SHA" (three subjects). The first two are encoded as real G1 start_dependency edges

    in this queue, and compile_repository_portfolio.py raises `ValueError` for any dependency edge that names
    a unit_id outside the acceptance-packet set ("missing start dependency packet"). Resolution: the
    ghpc-post-merge-main fact is instead recorded as a literal, checkable oracle string on ISSUE-566: "git
    rev-parse 28f394785aa8b13c4e6d2f21ad74c5e32a6a6dc5:skills/github-portfolio-control equals
    795de8e9ada4d0927f9a792760232ef75dda84e4 (ghpc frozen-plane binding, Shadow G1)" — verified true by this

T4. Superseded/consumed PR units (PR-562, PR-564, PR-565, PR-412, and the CONSUMED_BY_CONVERGENCE PRs 395,

    "salvageable-bytes-available" capability, NOT as blocked/terminal nodes. This is a deliberate modeling
    choice, not a forced one: their *disposition* (SUPERSEDED / CONSUMED_BY_CONVERGENCE) is recorded in
    `allowed_terminal_states`, while their node state reflects that the underlying bytes are genuinely
    available (verified in the current worktree HEAD, which already contains every one of these replay merges

    protects.

T5. Mechanism note (not a tension, a load-bearing correctness fact used above): compile_repository_portfolio.py
    fails closed with `ValueError: BLOCKED_PREDECESSOR: {...}` if a READY node's G1 (start_dependency)
    predecessor is itself non-READY. This governed several modeling choices in this artifact set: ISSUE-560 has
    NO start_dependencies (it is purely a completion-dependency sink fed by ISSUE-570, matching the task's own
    phrasing "560 aggregation node" — the abbreviated DAG "566 -> 567/559; 566+567 -> 568; 568 -> 569; 569+559
    -> 570" never lists an edge INTO 566 FROM 560); and PR-562/PR-564 (T4) are READY so that ISSUE-566's real
    G1 dependency on them does not deadlock the compile.
