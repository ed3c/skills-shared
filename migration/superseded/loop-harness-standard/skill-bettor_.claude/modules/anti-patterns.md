# Module: loop-harness-standard — 元層失敗前科(anti/)

> 屬 [`loop-harness-standard`](../SKILL.md)。**這一層的作用對象是 harness 自身**(閘、engine、
> workflow、量測探針),不是家族資產。小迴圈的 `anti/` 落在各沙盒;元層沒有沙盒,故落此。
> 格式沿用沙盒 `anti/` 慣例(症狀／根因／**禁回退**),不另造。
>
> **開工前先讀本檔**——與沙盒 `CLAUDE.md` 紀律 8「開工前先 `ls anti/` 讀失敗前科」同位。
> 下面第一條在**單一 session 內重犯 8 次**,原因就是當時沒有這個檔。

## anti: 壞探針回一個看起來合理的答案(2026-07-25/26,單 session 內 8 次)

**op/iter**:codex 判活 → 自動提示 → 標準入口 → 跨 repo 鏡像,共 7 支 workflow 期間

**症狀**:量測/驗證用的臨時腳本本身有缺陷,但**不會報錯**——它回一個語法合理、量級可信的數字或
判定,於是被當成證據採用。八次實例:

| # | 探針 | 壞在哪 | 假答案 |
|---|---|---|---|
| 1 | `ENGINE_UNDER_TEST` 逃生門 | engine.sh 由 `BASH_SOURCE` 推自己的 `ENGINE_DIR`,變異版放別處後 `SANDBOX` 解析錯 | 三個 case 全 die64,**看起來像「控制抓到了」** |
| 2 | parity fixture | 腳本用 `$0/..` 推 `REPO`,放 scratchpad 後指到錯的樹 | 唯讀檢查無素材可比,靜默通過 |
| 3 | 漂移計數 | `git ls-files \| head -400` 截斷 | 12 支漂移報成 7 支 |
| 4 | 漂移計數(二) | `FAIL` regex 撈到 WARN 行裡的「不 FAIL」 | 全 PASS 的輸出被算成紅,31% 假 none-path |
| 5 | fluff 齒測夾具 | 從黑名單檔 `head -3` 取到的是註解行,不是詞 | 單檔路徑也不觸發,**分不出是夾具錯還是回歸** |
| 6 | workflow 活性偵測 | BSD `find -newermt '-N minutes'` 解析失敗即匹配零筆 | 連續三次誤判「workflow 閒置」,據此併發改檔 |
| 7 | 懸空宣告計數 | `not Path(...) != None` 恆為 False | `miss` 永遠是空清單,報「0 支不存在」 |
| 8 | 跨類型參照 | 只用 repo-root 一種路徑基準,忽略沙盒相對 | 170 支假懸空(真值 59),總數 459 vs 真值 260 |

**根因**:探針與它要抓的缺陷是**同一類東西**——都是「沒有正控的一次性程式碼」。
而且失敗方向系統性偏向「看起來通過」:破掉的匹配回空集合、破掉的路徑回不存在、破掉的
條件回 False,這些在斷言裡都長得像「沒問題」。**沉默的錯誤比吵鬧的錯誤更容易被採信。**

**禁回退**:
1. **探針上場前先用已知答案雙向驗自己**——一個已知會命中、一個已知不會命中。
   兩個方向都對才准用它的結果。單向正控擋不住第 6、7 條(它們的失敗模式是「恆不命中」)。
2. **竄改型測試必須有 byte-guard**:證明你的竄改真的改到了位元組。第 5 條就是沒有 guard,
   而 2026-07-26 有 agent 因為補了 guard 才發現自己差點回報一個不存在的破口。
3. **路徑基準要枚舉不要假設**:repo-root 相對、檔案所在目錄相對、沙盒根相對——三種都試,
   全部找不到才算懸空(第 2、8 條)。
4. **腳本搬離原位就要重驗自我定位**:任何用 `$0/..`、`BASH_SOURCE`、`__file__` 推導根目錄的
   東西,複製到別處後那個推導就錯了(第 1、2 條)。
5. **數「出現次數」不要數「行數」**:`grep -c` 回的是 matching line count,單行多筆會誤判。
   要逐筆就 `grep -o | wc -l`。
6. **量級要有數量級預期**:報數字前先問「這個數量級合理嗎」。第 3、4、8 條若當時對照過
   已知規模(2177 追蹤檔 / 999 共用面),都會立刻露餡。

## anti: 修 A 缺陷時引入 B 缺陷,且 B 比 A 隱蔽(2026-07-25/26,3 次)

**op/iter**:自動提示 Goodhart 修正 / engine pre-flight / 跨 repo overlay 對稱性

**症狀**:針對已證實的缺陷做了正確方向的修法,但修法本身引入新缺陷,而新缺陷**不在原本的
驗證範圍內**,所以修完的驗證是綠的。三次實例:

| 修什麼 | 引入什麼 | 為何驗證沒抓到 |
|---|---|---|
| Goodhart 洩漏(作弊 driver 兩輪過關) | 遮蔽套在 dedup **之前**,中文語序把識別碼切掉 → M1..M6 塌成一條,**跨迭代差分整段消失** | 原驗證只問「還洩漏嗎」,沒問「差分還在嗎」——而差分是該組件的唯一增量 |
| engine pre-flight 擋非 drivable 沙盒 | 沒排除 `--dry-run`/`subagent`,而 spawn 類沙盒正是最該用 subagent 的那類 | 原驗證只做正控(該擋的有擋),沒做負控(不該擋的沒擋) |
| 漂移閘兩側判決不同 | 判準改成 `peer or self`,修好對稱性但把偽造面**從單側擴大到雙側** | 只驗了對稱性,沒驗修法對原有安全性質的影響 |

**根因**:修法的驗證繼承了「原缺陷的視角」——問的是「原症狀消失了嗎」,而不是
「這個組件所有的既有性質都還在嗎」。缺陷越是被精確描述,修法越容易只對著那個描述優化。

**禁回退**:
1. **修法的驗收必須包含該組件的「既有性質清單」**,不只是原症狀。清單來源=該檔 docstring
   自陳的價值主張(如 build_iter_feedback 明寫「跨迭代差分是唯一增量」)。
2. **正控與負控成對**:證明該擋的有擋 ∧ 該放的有放。三次裡有兩次是缺負控。
3. **安全性質的修改要問「這讓攻擊面變大還是變小」**——對稱性修法讓判準更寬,寬就是變大。

## anti: 閘一上線就大量紅 → 人學會忽略它(2026-07-25/26,3 次觸及)

**op/iter**:L2 沙盒正控接線 / parity 全掃擴面 / overlay 判準精確化

**症狀**:新閘接上或判準變嚴後,現況立刻產生大量紅(L2 一支沙盒 selftest 已紅 68 秒且沒人知道
紅多久;parity 擴面當天抓到 2 支舊世代沙盒;overlay 修正讓違規 204→216)。若就這樣上線,
第一週人就會學會跳過它。

**根因**:閘的「正確性」與「可用性」是兩件事。判準變嚴是進步,但**進步的代價是既有債一次現形**,
而人對「永遠紅的東西」的反應是關掉而不是修。

**禁回退**:上線前先量現況會紅幾條。多就**帶到期日的隔離帶**(既有形態=`PARITY_QUARANTINE`),
且隔離帶必須有:①到期日 ②理由 ③自我清理(轉綠要提示移除)。
⚠ 既有隔離帶的自我清理對「整支不 invoke」型是**死碼**——`_quarantined` 命中就 `continue`,
永遠走不到那條提示。設隔離帶時要確認清理路徑真的可達。

## anti: 閘存在能跑但沒接到「會複製 bug 的地方」(2026-07-26)

**op/iter**:codex driver feedback parity 上收

**症狀**:`test_driver_feedback_parity.sh` 只守自己那一個沙盒。結果同一個 bug(codex 分支自建
prompt、丟掉 `$FEEDBACK`)隨 `cp -r` 一路複製到 **6 支沙盒**,直到逐檔讀碼才被發現。

**根因**:守衛的覆蓋面按「它住在哪」決定,而 bug 的擴散面按「誰複製誰」決定。兩者不重合時,
守衛在自己的沙盒裡永遠是綠的。

**禁回退**:守衛的覆蓋面要對齊**擴散面**不是**所在地**。判準:這個 bug 會透過什麼路徑複製?
(`cp -r` 出新沙盒、模板實例化、跨 repo 鏡像)——守衛就要掃那個路徑的全集。

## anti: 跨 repo「同步刪除」不是刪兩個檔——每側有自己的衍生狀態(2026-07-26)

**op/iter**:`test_driver_feedback_parity.sh` 上收後兩側同步刪除

**症狀**:確認該檔冗餘(讀碼＋真跑:同沙盒同判決、差集斷言已被吸收、覆蓋 1→24)後兩側刪除。
sb 側同步更新了計數基線,**ts 側沒有,於是 ts 的 `test_dataflow_stats.sh` 從綠變紅**——
它斷言 `executable_scripts: 49`,而刪除讓實際變 48。我當下沒察覺,是後續跑 parity 才撞出來。

**根因**:把「同步刪除」當成**對稱的檔案操作**,但每個 repo 各自持有**衍生狀態**
(計數基線、寫死的斷言、清單快照),那些衍生量測的是**各自的庫存**,數值本來就不同
(sb 46 / ts 48)。刪同一支檔在兩側產生**不同的**衍生後果,所以修法也必須各自做一次。

**禁回退**:跨 repo 的任何增刪,除了檔案本身,要同時問「哪些衍生狀態量測了這個庫存」。
最少要查:計數基線(`baselines/*.json`)、寫死數字的測試、清單型宣告區塊。
**判準是「兩側各自跑一次該側的驗證」,不是「兩側檔案一致」**——後者為真時前者仍可能紅。

## anti: 治理人閘只覆蓋了它所治理事實的一份副本(2026-07-26)

**op/iter**:`baselines/dataflow-stats.json` 的 governed 更新(47→46)

**症狀**:repo 刻意讓基線更新走 governance packet + `admit_edge: human_required_before_baseline_update`,
防止靜默改基線。走完整套正規流程(更新 packet 的 drift_summary → `update_dataflow_baseline.py --write`)
之後,**沙盒 selftest 仍然紅**。因為同一個數字還寫死在 `scripts/test_dataflow_stats.sh` 的
`assert_contains '"scripts_total": 47'`,而 governed 腳本**只更新 JSON 那一份**。

更難追的是錯誤訊息:`FAIL: /var/.../plan-truth-stats.XXXX/current.json missing: "scripts_total": 47`
——它指向 temp 檔,不指向那個寫死的字面量。看起來像「計算出來的值不對」,實際是「斷言方沒跟上」。

**根因**:治理機制的**作用域**是它自己宣告的那個 artifact(`baseline_file: baselines/...json`),
而被治理的**事實**(這個數字)有兩份副本。人閘擋住了靜默改動,卻沒讓兩份副本一起走。
⇒ **為防漂移而設的閘,自己活在漂移面上。**

**禁回退**:
1. 設人閘前先數**該事實有幾份副本**;閘只覆蓋一份就是假保護。
2. 寫死的期望值是副本。測試該**讀基線檔**,或由同一支 governed 腳本一起更新。
3. 錯誤訊息要指向**該改的地方**。指向衍生產物(temp/current.json)會讓人往錯的方向查。
4. 判「governed 流程走完了沒」的標準是**跑一次該層的驗證**,不是「腳本回了 PASS」。

## anti: 零命中是最需要當場重驗的答案(2026-07-26)

**op/iter**:基座 6 環境自足普查,判準 C2「驗證期改環境」掃描

**症狀**:掃 60 支 tracked `verify.sh`/`selftest.sh` 找「驗證期安裝套件」,regex `pip install`
回 **0 命中**——而我明知 evals-gate 那支有這行。真因是 **shell 引號穿插打斷了 regex 字面量**:
原始碼寫成 `"$HERE/venv/bin/pip" install`,`pip` 與 `install` 之間夾了一個 `"`。
改成 `(pip|npm|uv)["']?[[:space:]]+install` 後 known-hit=1 / known-miss=0,真值是 **2 支**。

**根因**(兩條,都不在第一條的六條禁回退裡):
1. 那六條把雙向驗寫成「探針**上場前**」的一次性動作,沒把「**回零**」列為觸發條件。
   但第一條表列的 8 個實例中有 3 個(#5/#6/#7)正是零命中形態——零是本檔最常見的假答案,
   卻沒有對應的觸發規則。實犯過程就是:C3 做了雙向驗,C2 覺得「只是個 grep」而略過。
2. **grep 打原始碼時,字面量會被引號、變數插值、續行切開**。shell 尤其嚴重
   (`"$VAR"/bin/cmd arg`、`\` 續行、`$( )` 巢狀)。這是通用誤判面,不在既有六條裡。

**禁回退**:
1. **回零即觸發重驗**,不論上場前驗過沒有。零命中要當場找一個**已知必中**的樣本餵進去;
   它若也回零,是探針壞了不是資料乾淨。
2. grep 原始碼時字面量之間要容忍引號/空白/變數(`["']?[[:space:]]+`),
   或拆成獨立 token 分別找再驗同行,而非整串比對。
3. 報「乾淨/沒有/0 支」的證據強度要求**高於**報「找到 N 支」——後者自帶樣本可覆核,前者沒有。

## anti: 探針的壽命維度——一次性量測錯一次,常設閘錯是永久且永遠綠(2026-07-26)

**op/iter**:基座 6 判準 C1–C3 從「量測」升格為「常設閘」

**症狀**:第一條表列的 8 個實例全是**一次性量測探針**——錯一次,報一個假數字,下次重量就露餡。
但同一批判準一旦接進 commit 層變成**常設閘**,同樣的破法後果完全不同:不是報錯一次,
而是**永久漏抓且永遠綠**。沒有人會去重量一個綠的閘。

**根因**:探針的正確性要求被當成常數,但它其實是**壽命的函數**。一次性探針的錯誤有自然的
偵測時機(下次量測);常設閘的錯誤**沒有任何偵測時機**,除非另外有閘的閘。
這就是 `check_all_skills.py --layer meta` 存在的理由。

**禁回退**:
1. 判斷探針要不要接成常設閘時,**先把它的自證寫完再接**。順序反了會有一段
   「已經在擋 commit 但沒人驗過它會不會擋錯」的窗口。
2. 常設閘的自證必須含**負控**(該放的有放),不只正控。WARN-only 閘尤其——
   它本來就不擋,壞掉最不容易被察覺。
3. 一次性探針可接受「單向驗 + 量級合理性」;常設閘不行,它要雙向 + byte-guard。
   **成本差異是刻意的,對應的是偵測時機的差異。**
